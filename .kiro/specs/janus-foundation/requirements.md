# Janus 要件定義書

## 概要

Janus は、GROWI の代替となる軽量なナレッジベースシステムである。非力なマシンや Android 端末でも動作することを目的とし、同一のフロントエンドで次の 2 つの運用形態を両立する。

- **ローカルモード**: 端末内で完結。サーバープロセス不要・root 不要。データは端末内（IndexedDB）に保存。主に Android 端末単体・個人利用を想定。
- **サーバーモード**: Django + REST API による Web サーバー/クライアント方式。複数人・無制限のページ数・地図枚数に対応。CAD 自動変換を含む全機能を提供。

名前の由来は、二つの顔（ローカル / サーバー）を持つローマ神話の神 Janus による。

### 設計の中核方針

- フロントエンドは **1 つだけ** 実装する（React + TypeScript + PWA）。
- フロントが叩く **REST API の形を 1 つに統一** する。ローカルモードでは IndexedDB を読み書きする JS 実装が、サーバーモードでは Django のエンドポイントが、同じ API 契約を満たす。
- 既存プラグイン（growi-plugin-custom-map）の地図ビューア / エディタのロジックを可能な限り流用する。
- GROWI からのデータ移行は行わない（新規構築）。
- 第一段階ではローカル ⇔ サーバー間の同期は実装しない（描画・ページとも「取り込み（A 案）」で統一）。双方向同期は将来拡張として設計に余地を残す。
- **Elasticsearch は採用しない**（軽量・ローカル完結の方針と矛盾するため）。検索は後述の軽量手段で段階的に実装する。

## 開発段階とスコープ

本プロジェクトは段階的に構築する。各要件には対応段階を明記する。コードは第一段階の合意後に着手する。

- **フェーズ 1（第一段階 / 本 Spec の実装対象）**: サーバーモードの基盤。
  - ページ CRUD、Markdown 表示、地図記法の表示、サーバーモードの**認証・ユーザー管理**。
  - 統一 API 契約の定義（この時点ではサーバー実装のみ）。
- **フェーズ 2（比較的早期に着手）**: 権限管理、リビジョン機能。
- **フェーズ 3（中盤）**: コメント / メモ、draw.io 描画（サーバー）、CAD 自動変換（サーバー）、ローカルモード（PWA + IndexedDB）、地図 GUI 編集・現場写真添付。
- **フェーズ 4（ローカル実用化の直前 = 最終段階手前）**: 全文検索（ローカル N-gram / サーバー FTS）。
- **将来拡張（本プロジェクトのスコープ外）**: ローカル ⇔ サーバーの手動エクスポート/インポート同期（B 案）、全文検索の高精度化（PGroonga 等）。

> フェーズ 2 以降の要件も本書に記載するが、詳細設計・タスク化はフェーズ到達時に別途行う。本 Spec（janus-foundation）の実装対象はフェーズ 1 とする。

## 用語

- **ページ**: Markdown 本文を持つナレッジの最小単位。階層パスを持つ。
- **リビジョン**: ページ本文の 1 時点のスナップショット。
- **地図記法**: 画像/CAD 上にマーカーを配置する `:::custom-map` ディレクティブ。既存プラグインの記法を踏まえつつ、アセット参照は Janus のアセットライブラリ方式（後述）に合わせる。
- **アセット**: 画像・CAD（変換後 SVG）・描画などのバイナリ/ファイル資源。ページには従属せず、独立した**アセットライブラリ**（共有リソース）として管理する。複数のページから参照できる。
- **アセットライブラリ**: アセットを階層フォルダで整理する共有の保管領域。GROWI プラグインの map_library/media_library が「アセット登録前の仮置き場」だったのとは異なり、Janus には仮置き場はなく、アップロードされたファイルは（必要に応じて変換のうえ）直接ライブラリへ登録される。
- **フォルダ**: アセットライブラリ内の階層ノード。親フォルダへの参照で木構造を成す（例 `本館/2F`、`別館/2F`）。
- **描画**: draw.io（diagrams.net）形式の図。XML（mxGraph）で保持する。
- **ストレージアダプタ**: 統一 API 契約を、ローカル（IndexedDB）/ サーバー（REST）それぞれで実装する層。

## 要件

### 要件 1: 統一 API 契約とストレージアダプタ 〔フェーズ 1〕

**ユーザーストーリー:** 開発者として、ローカルモードとサーバーモードで同一のフロントエンドコードを使いたい。そうすれば二重開発を避け、保守を一本化できる。

#### 受け入れ基準

1. WHEN フロントエンドがページ・リビジョン等のデータ操作を行う THEN システム SHALL 単一の API 契約（インターフェース）を介して行う。
2. WHEN 実行環境がサーバーモードである THEN システム SHALL API 契約を Django REST エンドポイントで満たす。
3. WHEN （フェーズ 3 で）ローカルモードを追加する THEN システム SHALL 同一の API 契約を IndexedDB ベースの実装で満たし、フロントの画面コードを変更しない。
4. THE API 契約 SHALL 検索機能を 1 つのインターフェースに閉じ込め、実装（FTS/N-gram 等）を差し替え可能とする。

### 要件 2: ページ管理（CRUD・階層・Markdown） 〔フェーズ 1〕

**ユーザーストーリー:** 利用者として、技術資料を Markdown でページとして作成・編集・整理したい。そうすれば無制限に知識を蓄積できる。

#### 受け入れ基準

1. WHEN 利用者がページを新規作成する THEN システム SHALL 一意なパス（例 `/docs/intro`）と Markdown 本文を保存する。
2. WHEN 利用者がページを編集して保存する THEN システム SHALL 本文を更新する（リビジョン記録はフェーズ 2 の要件 6 に従う）。
3. WHEN 利用者がページを閲覧する THEN システム SHALL Markdown をレンダリングして表示する。
4. WHEN 利用者がページを削除する THEN システム SHALL ページを削除する。
5. THE システム SHALL ページ数に固定の上限を設けない。
6. WHEN 利用者がパスでページを探す THEN システム SHALL 階層的に一覧・ナビゲートできる。
7. IF 既に同一パスのページが存在する状態で新規作成する THEN システム SHALL 重複を拒否し利用者に通知する。

### 要件 3: 地図機能の表示（既存プラグインの移植） 〔フェーズ 1 は表示、GUI 編集はフェーズ 3〕

**ユーザーストーリー:** 利用者として、図面や画像の上にマーカーを配置した地図を閲覧したい。そうすれば現場の位置情報を視覚的に把握できる。

#### 受け入れ基準

1. THE システム SHALL 地図記法（`:::custom-map` とマーカー箇条書き）を解釈し表示する。アセット参照は Janus のアセットライブラリ方式に合わせる（要件 14）。〔フェーズ 1〕
2. WHEN 地図を表示する THEN システム SHALL パン・ズーム・90 度単位の回転・マーカー最小化/復帰・写真/説明ポップアップを提供する。〔フェーズ 1〕
3. WHEN マップ画像・マーカー写真を参照する THEN システム SHALL アセットライブラリから、記法の参照指定（`file:`/`alias:` と基準フォルダ、要件 14）に従って解決する。〔フェーズ 1〕
4. WHEN 利用者が編集画面で地図を作成/編集する THEN システム SHALL GUI でマーカーを配置し記法を生成/更新する。〔フェーズ 3〕
5. WHEN 利用者が Android 端末で現場写真を撮影する THEN システム SHALL その写真をマーカーの参照写真として添付できる（カメラ起動を含む）。〔フェーズ 3〕

### 要件 4: サーバーモードの認証・ユーザー管理 〔フェーズ 1〕

**ユーザーストーリー:** 運用者として、テストでネット上に公開する際に不用意なアクセスを防ぎたい。そうすれば安全に外部公開して検証できる。

#### 受け入れ基準

1. THE サーバーモード SHALL ユーザーの登録・ログイン・ログアウトを提供する。
2. WHEN 未認証の利用者が保護されたページ/API にアクセスする THEN システム SHALL アクセスを拒否し認証を要求する。
3. THE システム SHALL パスワードを安全に（ハッシュ化して）保存する。
4. THE システム SHALL 少なくとも「管理者」と「一般利用者」を区別できる（詳細な権限はフェーズ 2 の要件 5）。
5. WHEN 認証済み利用者が操作する THEN システム SHALL その操作者を記録できる（リビジョン・コメントの作者表示に用いる）。
6. THE システム SHALL Django 標準の認証機構を基盤とする。

### 要件 5: 権限管理 〔フェーズ 2〕

**ユーザーストーリー:** 運用者として、ページの閲覧・編集を利用者やグループ単位で制御したい。そうすれば共有範囲を適切に保てる。

#### 受け入れ基準

1. THE システム SHALL ページ単位（または階層単位）で閲覧・編集の可否を制御できる。
2. WHEN 権限のない利用者が操作する THEN システム SHALL その操作を拒否する。
3. THE システム SHALL 利用者をグループに所属させ、グループ単位で権限を付与できる。

### 要件 6: リビジョン機能 〔フェーズ 2〕

**ユーザーストーリー:** 利用者として、ページの変更履歴を残し、過去の状態を確認・復元したい。そうすれば誤編集を取り消し、変遷を追える。

#### 受け入れ基準

1. WHEN ページ本文が保存される THEN システム SHALL その時点のリビジョン（本文・日時・編集者）を記録する。
2. WHEN 利用者がページの履歴を開く THEN システム SHALL リビジョンの一覧を新しい順に表示する。
3. WHEN 利用者が 2 つのリビジョンを選ぶ THEN システム SHALL その差分（追加・削除行）を表示する。
4. WHEN 利用者が過去のリビジョンを選んで復元する THEN システム SHALL その本文を新しいリビジョンとして保存する（履歴は失わない）。
5. IF 本文に変更がない保存操作が行われた THEN システム SHALL 不要な重複リビジョンを作成しないことが望ましい。
6. THE リビジョン機能 SHALL ローカルモードでも誤編集の救済手段として機能する。

### 要件 7: コメント / メモ機能 〔フェーズ 3〕

**ユーザーストーリー:** 利用者として、ページに注記やメモを残したい。そうすれば補足情報や後で見返す覚書を記録できる。

#### 受け入れ基準

1. WHEN 利用者がページにコメントを追加する THEN システム SHALL コメント本文・日時・（サーバーモードでは）投稿者を当該ページに紐付けて保存する。
2. WHEN 利用者がページを閲覧する THEN システム SHALL そのページのコメント一覧を表示する。
3. WHEN 利用者が自分のコメントを編集・削除する THEN システム SHALL 変更を反映する。
4. WHEN ページが削除される THEN システム SHALL そのページに紐付くコメントを連動削除する。

### 要件 8: CAD 変換 〔フェーズ 3〕

**ユーザーストーリー:** 利用者として、CAD 図面（dxf/jww）を地図として使いたい。そうすれば図面を手動で画像化せずに扱える。

#### 受け入れ基準

1. WHEN サーバーモードで CAD（.dxf/.jww）をアップロードする THEN システム SHALL 既存変換ロジック相当で SVG に変換し、その SVG を**アセットライブラリに登録する**（要件 14）。元の CAD ファイルは保持しなくてよい。
2. WHEN サーバーモードで CAD をアセット登録する THEN システム SHALL 向き（0/90/180/270 度）を焼き込んだ SVG として登録できる。
3. WHEN ローカルモードで CAD を使う THEN システム SHALL PC 側で事前変換した画像/SVG の取り込みで対応する（端末内での CAD 変換は行わない）。
4. IF サーバーモードで変換が未稼働/失敗する THEN システム SHALL アップロードを失敗として通知する（アセット未登録のまま、通常画像の案内等にフォールバックしてよい）。
5. THE CAD 変換 SHALL アセットライブラリへの登録の一手段として位置づけ、変換ロジックを後から差し替え可能にする。

### 要件 9: 描画機能（draw.io 埋め込み） 〔フェーズ 3〕

**ユーザーストーリー:** 利用者として、ページ内に図を作図したい。そうすれば文章だけでは伝わらない構造を図示できる。

#### 受け入れ基準

1. WHEN サーバーモードで利用者が描画を作成/編集する THEN システム SHALL draw.io（diagrams.net）埋め込みエディタを提供し、図を XML（mxGraph）としてページに保存する。
2. WHEN 描画を含むページを閲覧する THEN システム SHALL 図をレンダリング表示する。
3. WHEN ローカルモードで図が必要な場合 THEN システム SHALL 外部で作図した画像/SVG の取り込みで対応する（第一段階では端末内 draw.io 編集・同期は行わない）。
4. THE システム SHALL 描画データを、将来の手動エクスポート/インポート同期（B 案）を阻害しない形式で保持する。

### 要件 10: ローカルモード（PWA / オフライン / 端末保存） 〔フェーズ 3〕

**ユーザーストーリー:** 利用者として、Android 端末単体でサーバーもインストールも立てずにナレッジベースを使いたい。そうすれば現場でオフラインでも閲覧・編集できる。

#### 受け入れ基準

1. THE システム SHALL ローカルモードで root 権限・常駐サーバープロセスを要さない。
2. WHEN 利用者が端末でページ/地図を作成・編集する THEN システム SHALL データを端末内（IndexedDB）に保存する。
3. THE システム SHALL PWA としてインストール可能（ホーム画面追加）であり、オフラインで起動・動作する。
4. WHEN 利用者が現場で写真を撮る THEN システム SHALL 端末のカメラから画像を取り込み端末内に保存する。
5. THE システム SHALL ローカルモードで図面数十枚・単一利用者の規模で快適に動作する。
6. WHEN 利用者がローカルモードの管理機能にアクセスする THEN システム SHALL パスワードを要求する（簡易保護。サーバーモードのような多ユーザー認証は行わない）。

### 要件 11: 全文検索 〔フェーズ 4〕

**ユーザーストーリー:** 利用者として、ページ本文を串刺しで検索したい。そうすれば蓄積した資料から目的の記述を素早く見つけられる。

#### 受け入れ基準

1. THE サーバーモード SHALL 全文検索を SQLite FTS5（N-gram トークナイザ）で実装する。
2. THE ローカルモード SHALL 全文検索をブラウザ内 N-gram インデックスで実装する（辞書・形態素解析器・常駐サーバーを要さない）。
3. WHEN 利用者が検索語を入力する THEN システム SHALL 本文に一致するページを一覧し、該当箇所を提示する。
4. THE 検索実装 SHALL 要件 1 の統一 API 契約の検索インターフェースを満たし、将来 PostgreSQL + PGroonga 等への差し替えを可能とする。
5. THE システム SHALL 日本語検索を N-gram 方式で成立させる（Elasticsearch を用いない）。

### 要件 12: サーバーモード（Django / スケーラビリティ / 軽量性） 〔フェーズ 1 で基盤、以降で拡充〕

**ユーザーストーリー:** 運用者として、サーバー/クライアント方式で複数人・無制限の規模に対応したい。そうすれば組織の共有ナレッジベースとして使える。

#### 受け入れ基準

1. THE システム SHALL サーバーモードを Python/Django（＋ Django REST Framework）で実装する。
2. THE システム SHALL データベースを SQLite（小規模）と PostgreSQL（本格運用）で設定切替可能とする。
3. THE システム SHALL ページ数・地図枚数・利用人数に固定上限を設けない。
4. THE システム SHALL GROWI のような重量級ミドルウェア（MongoDB・Elasticsearch 等）への依存を要さず、非力なマシンで動作する。
5. THE サーバーモード SHALL root 権限なしで起動できる（上位ポートでの待受を許容する）。

### 要件 13: 軽量性・移植性（全体） 〔全フェーズ共通〕

**ユーザーストーリー:** 利用者として、GROWI より軽く、非力なマシンや Android でも動くシステムが欲しい。

#### 受け入れ基準

1. THE システム SHALL 最小構成でサーバーモードを「Python 1 プロセス + SQLite 1 ファイル」まで縮小できる。
2. THE システム SHALL ローカルモードでサーバープロセスなしに動作する。
3. THE システム SHALL 既存の 2 リポジトリとは独立した新規リポジトリ（`/home/kawakin/git/knowledge-base/janus`）として構築する。

### 要件 14: アセットライブラリ（独立リソース・階層管理・参照解決） 〔フェーズ 1〕

**ユーザーストーリー:** 利用者として、地図画像や図面を特定ページに縛られない共有ライブラリとして登録・整理し、どのページの地図記法からも参照したい。そうすれば同じ図面を複数ページで使い回し、建物・階などの単位で整理できる。

#### 背景（GROWI プラグインとの違い）

GROWI プラグインでは、プラットフォームの制約（添付はページ単位、閲覧権限もページ単位、CAD 変換に別 API サーバーが必要）から、アセットを「ページ添付」として扱い、map_library/media_library という仮置き場を介していた。Janus は自前バックエンドを持つため、これらの制約・仮置き場は不要とする。アセットはページから独立した共有リソースとして一元管理し、CAD 変換は Janus サーバーモード内の登録手段の一つとする（別 API サーバーは不要）。

#### 受け入れ基準

1. THE システム SHALL アセットを**ページから独立した共有リソース**として管理する（ページへの従属・ページ FK を持たない）。1 つのアセットを複数ページの地図記法から参照できる。
2. THE システム SHALL アセットを**階層フォルダ**で整理できる。フォルダは親フォルダへの参照で木構造を成す（例 `本館/2F`、`別館/2F`）。フォルダ構造は DB で管理し、ファイル実体はストレージ上にフラットに保存してよい（ツリー変更が容易になるよう、物理配置と論理階層を分離する）。
3. THE 各アセット SHALL **ファイル名（filename）**と**別名（alias）**の 2 つの名前を持ち、いずれでも参照できる。alias は人がつける登録名（別名）で、省略可とする。
4. THE システム SHALL filename・alias それぞれを**同一フォルダ内で一意**とする（異なるフォルダであれば同名を許す。例 `本館/2F/map.png` と `別館/2F/map.png` は共存できる）。
5. WHEN アセットを別フォルダへ移動する THEN システム SHALL 移動先フォルダに同名（filename または alias）が既に存在する場合は**移動を禁止**し、利用者に通知する。
6. WHEN サーバーモードでファイルをアップロードする THEN システム SHALL 仮置き場を介さず、指定フォルダへ直接アセットとして登録する。画像はそのまま、CAD は SVG へ変換して（要件 8）登録する。
7. THE システム SHALL アセットライブラリの操作（フォルダ作成・一覧・アセット登録・一覧・参照解決）を統一 API 契約（要件 1）の AssetClient に閉じ込め、ローカル/サーバー両モードで同契約を満たせるようにする。
8. 〔フェーズ 1 スコープ〕 フェーズ 1 では「階層化できる器」（独立アセットモデル・フォルダ木・filename/alias・フォルダ内一意・移動時重複禁止・アップロード/一覧/参照解決の API と最小 UI）までを対象とする。CAD 変換（要件 8）・フォルダの GUI による作成/移動の作り込み・現場写真撮影（要件 3-5, 10-4）はフェーズ 3 とする。

#### 地図記法でのアセット参照（要件 3 と連動）

9. THE 地図記法 SHALL アセット参照に次の指定子を用いる（過去の記法互換は要求しない）:
   - `filename:`（`file:` と省略可）: **ファイル名**で参照する。
   - `aliasname:`（`alias:` と省略可）: **別名（alias）**で参照する。
10. THE 地図記法 SHALL 参照の基準となるフォルダをコンテナ属性で指定できる（基準フォルダ）。個々の参照値にスラッシュを含めてフォルダを明示した場合は、その指定を優先する（基準フォルダからの相対または絶対のフォルダ解決を許す）。
11. IF 1 つの参照に filename 指定と alias 指定が同時に与えられた THEN システム SHALL **先に出現した指定を優先**して名前解決し、解決に失敗した場合に 2 つ目の指定で解決を試みる（GUI で記法を生成する場合は二重指定を避ける）。
12. WHEN 名前解決を行う THEN システム SHALL 「フォルダパス → フォルダ ID → 同一フォルダ内の (filename|alias) 一意検索」の順で解決する（DB 上はフォルダ ID 起点の一意制約で一意に定まる）。解決できない場合は既存同様に「見つかりません」を表示する（要件 9）。
