# Janus フェーズ 2 要件定義書（権限管理・リビジョン）

## 概要

本書は Janus フェーズ 2 の要件を定義する。フェーズ 1（janus-foundation）で構築したサーバーモード基盤の上に、foundation 要件書の **要件 5「権限管理」** と **要件 6「リビジョン機能」** を実装レベルまで具体化する。

フェーズ 1 は完了・コミット済み（最新 `dfba977` 独立アセットライブラリ移行）であり、本フェーズは既存の `Page` モデル・ページ CRUD API（`/api/pages` 系）・DRF Token 認証・Django 標準 `auth.User`/`Group`・フロントの `StorageClient` 契約と編集画面（`PageEditPage`）を起点に拡張する。フェーズ 1 の完了判定（既存テスト・既存 API 契約）を覆さず、原則として **phase2 での追加** によって機能を積み上げる。foundation の文書・契約に手を入れざるを得ない箇所は本書で「foundation 変更」と明示する。

本フェーズのスコープは次の 2 軸に限定する。

- **権限管理（要件 5）**: ページ単位の閲覧・編集制御、階層継承、Allow/Deny、ユーザー/グループ単位の権限付与、デフォルト公開/非公開ポリシー、権限に基づく一覧の見え方、認証なし/権限なし時の HTTP 応答。
- **リビジョン機能（要件 6）**: ページ本文のスナップショット記録、履歴一覧、差分表示、復元、重複リビジョン抑制、作者・ページ削除時の挙動。

本フェーズでは **アプリケーションコードは変更しない**。本書は要件定義のみを扱い、設計・実装は後続ステップで行う。

### 対象リポジトリ・起点ファイル

- バックエンド: `backend/api/models.py`（`Page`/`Folder`/`Asset`）、`serializers.py`、`views.py`、`urls.py`、`tests_*.py`、`backend/janus/settings.py`
- フロントエンド: `frontend/src/storage/types.ts`（`StorageClient` 契約）、`rest-client.ts`、`frontend/src/pages/*`（`PageViewPage`/`PageEditPage`/`PageListPage`/`LoginPage`/`AssetLibraryPage`）、`frontend/src/markdown/custom-map`

### 前提となる現状（フェーズ 1 の確認結果）

- 認証は DRF `TokenAuthentication`。既定権限は `JANUS_REQUIRE_AUTH`（既定 true）により全 API `IsAuthenticated`、false なら `AllowAny`。`login`/`me` のみ `AllowAny` 明示。**現状はページ単位・オブジェクト単位の権限制御は存在しない**（認証済みなら全ページを読み書き可能）。
- `Page` は `path` 一意・`body`（Markdown 生テキスト）・`created_by`/`updated_by`（`SET_NULL`）を持つ。保存経路は `PageDetailView`（`POST`/`PUT`/`DELETE`、`?path=` クエリ）。保存のたびに `Page.body` を上書きし、履歴は残らない。
- ユーザーは Django 標準 `auth.User`。管理者は `is_staff`/`is_superuser`。`auth.Group` は利用可能だが未使用。
- アセット（`Folder`/`Asset`）はページから独立。現状ページ権限とは無関係。
- DB は SQLite 既定、PostgreSQL は設定切替可能（`DATABASE_URL`）。**ユーザー方針により PostgreSQL 対応は後回しでよい**。本フェーズは SQLite で成立し、かつ Postgres 移行を阻害しない制約・クエリとすることを目標とする。

## 用語（本フェーズで用いる定義）

- **主体（principal）**: 権限付与の対象。ユーザー（`auth.User`）またはグループ（`auth.Group`）。
- **権限エントリ（permission entry）**: 「あるページに対し、ある主体に、ある操作（閲覧/編集）を Allow または Deny する」1 レコード。
- **実効権限（effective permission）**: 階層継承・Allow/Deny・デフォルトポリシーを合成した、ある主体のあるページに対する最終的な可否。
- **閲覧（view）**: ページ本文・メタ情報・リビジョン履歴の取得。
- **編集（edit）**: ページ本文/タイトルの作成・更新・削除、リビジョン復元。
- **デフォルトポリシー**: 明示的な権限エントリが一切作用しないページに適用する既定の可否（公開/非公開）。
- **リビジョン**: ある時点のページ本文の全文スナップショット（本文・日時・編集者）。

## 要件

### 要件 P2-1: ページ単位の閲覧・編集権限 〔foundation 要件 5-1〕

**ユーザーストーリー:** 運用者として、ページごとに閲覧・編集の可否を主体（ユーザー/グループ）単位で設定したい。そうすれば共有範囲をページ単位で正確に制御できる。

#### 受け入れ基準

1. THE システム SHALL ページに対して「閲覧（view）」「編集（edit）」の 2 操作について、主体（ユーザーまたはグループ）ごとに Allow/Deny を設定できる権限エントリを保持する。
2. THE 権限エントリ SHALL 対象ページ・主体種別（user/group）・主体 ID・操作（view/edit）・効果（allow/deny）を一意に識別できる。
3. WHEN 同一（ページ, 主体, 操作）に重複する権限エントリを登録しようとする THEN システム SHALL 重複を拒否する（409）か、既存を更新する（本書では **重複拒否 + 更新用 PATCH** を推奨。理由: エントリの意図を明示的にし、暗黙上書きの事故を避ける）。
4. THE 編集権限（edit）を持つ主体 SHALL 当該ページの閲覧（view）も可能とする（edit は view を含意する）。
5. WHEN 管理者（`is_superuser` が真）が操作する THEN システム SHALL 権限エントリやデフォルトポリシーに関わらず全ページの閲覧・編集を許可する（運用者が自分をロックアウトしない安全弁）。
6. THE 権限設定の読み書き（一覧・付与・取消・更新）SHALL REST API で提供し、対象ページの編集権限を持つ主体または管理者のみが行える。

> **推奨の記録（権限モデルの土台）**: Django 標準の `ModelPermission`（モデル単位）やオブジェクト権限ライブラリ（django-guardian 等）ではなく、**Janus 独自の `PagePermission` モデル**で表現することを推奨する。理由: 権限の単位が「個々のページ（path 階層）」であり、階層継承・Allow/Deny・デフォルトポリシーという Janus 固有の合成規則が必要で、標準の全モデル一律権限やオブジェクト権限フレームワークでは階層継承を素直に表現できないため。主体には Django 標準の `auth.User`/`auth.Group` をそのまま使う（foundation 要件 4-6・5-3 と整合、グループ管理を再発明しない）。この選択はセキュリティ境界に関わるため、設計レビューで最終確認する（下記「ユーザー判断が必要な未確定事項」U-1）。

### 要件 P2-2: 階層継承 〔foundation 要件 5-1「または階層単位」〕

**ユーザーストーリー:** 運用者として、親ページ（またはパス階層）に設定した権限を配下ページへ継承させたい。そうすれば 1 ページずつ設定せずツリー単位で共有範囲を管理できる。

#### 受け入れ基準

1. THE システム SHALL ページの権限を、`path` の階層（例 `/docs` → `/docs/intro` → `/docs/intro/deep`）に沿って祖先から子孫へ継承する。
2. WHEN あるページに自身の権限エントリが存在しない THEN システム SHALL 最も近い祖先ページの実効権限を継承する。
3. WHEN あるページと、その祖先に、同一主体・同一操作の権限エントリが両方存在する THEN システム SHALL **より近い（path が長い）祖先または自身の設定を優先**する（具体性の高い設定が勝つ）。
4. WHEN 同一ページ・同一主体・同一操作で Allow と Deny が競合しうる場合（ユーザー経由の allow とグループ経由の deny 等、同一階層レベル）THEN システム SHALL **Deny を優先**する（安全側）。ただし祖先の Deny より自身の Allow が近ければ自身の Allow が勝つ（基準 3 が基準 4 に優先する: まず階層的近さ、同レベル内で Deny 優先）。
5. THE 継承解決 SHALL 祖先に権限エントリが一切無ければデフォルトポリシー（要件 P2-3）に委ねる。
6. THE 継承の計算 SHALL `path` 文字列の階層分解（`/docs/intro` の祖先は `/docs/intro`, `/docs`, ルート）に基づき、別途の親子 FK を `Page` に追加せず実現できることを基本とする（foundation の `Page` スキーマ非破壊を優先）。

> **設計上の注意（foundation 整合）**: foundation の `Page` は `path` 一意のフラットモデルで、親子 FK を持たない。階層継承は path 文字列から祖先列を導出して解決する方式を推奨する。中間の祖先 path に実ページが存在しない場合（例 `/docs/intro` はあるが `/docs` ページは無い）でも、権限エントリは「存在しないパスにも設定できる仮想ノード」として扱うか、「実在ページにのみ設定可」とするかを設計で確定する（本書では実装容易性と直感性から **権限エントリは任意の path プレフィックスに設定可能（仮想ノード許容）** を推奨。U-2 に記録）。

### 要件 P2-3: デフォルトポリシー（公開/非公開） 〔foundation 要件 4-2・5 の既定挙動の明確化〕

**ユーザーストーリー:** 運用者として、権限が明示されていないページの既定の見え方を、インスタンス単位で公開/非公開に切り替えたい。そうすれば「原則非公開・許可したものだけ公開」または「原則公開・禁止したものだけ非公開」の運用を選べる。

#### 受け入れ基準

1. THE システム SHALL 「認証済みユーザーに対する既定の閲覧/編集可否」を決めるデフォルトポリシー設定を持つ（環境変数で切替。例 `JANUS_DEFAULT_PAGE_VIEW` / `JANUS_DEFAULT_PAGE_EDIT`）。
2. THE デフォルトポリシー SHALL 既定値を **閲覧=許可・編集=許可（＝フェーズ 1 と同じ全認証ユーザーが読み書き可）** とする。理由: フェーズ 1 の挙動を破壊せず、権限エントリを設定したページだけが段階的に制限されるようにする（後方互換・移行の安全性）。
3. WHEN デフォルトポリシーを「非公開」に設定する THEN システム SHALL 権限エントリで明示的に Allow された主体のみに当該操作を許可する。
4. THE デフォルトポリシー SHALL 認証有無（`JANUS_REQUIRE_AUTH`）とは独立に、認証済みユーザー間の可否を決める。未認証アクセスの扱いは要件 P2-6 に従う。
5. THE 管理者（`is_superuser`）SHALL デフォルトポリシーに関わらず常に許可される（要件 P2-1-5 と一致）。

### 要件 P2-4: グループ単位の権限 〔foundation 要件 5-3〕

**ユーザーストーリー:** 運用者として、利用者をグループに所属させ、グループ単位で権限を付与したい。そうすれば個人ごとの設定を避け、組織構造で共有範囲を管理できる。

#### 受け入れ基準

1. THE システム SHALL Django 標準 `auth.Group` を主体として権限エントリを付与できる。
2. WHEN あるユーザーが所属する複数グループに異なる権限エントリがある THEN システム SHALL それらを合成し、同一階層レベルでは Deny を優先する（要件 P2-2-4 と一致）。
3. THE システム SHALL ユーザーのグループ所属（追加・削除）と、グループの作成・一覧を管理する手段を提供する。手段は **Django admin を基本**とし、必要最小限の管理 API のみ本フェーズで追加する（グループ CRUD の本格 UI はスコープ外、U-3 に記録）。
4. WHEN ユーザー直接付与の権限エントリとグループ経由の権限エントリが同一ページ・同一操作で競合する THEN システム SHALL **ユーザー直接付与を、同一階層レベル内ではグループより優先**する（より具体的な指定が勝つ）。ただし階層的近さ（要件 P2-2-3）が優先条件として上位にある。

> **合成順序の明確化（設計で固定する優先順位）**: ①階層的近さ（path が長い祖先/自身が勝つ）→ ②同一ノード内では主体の具体性（user 直接 > group）→ ③なお競合する場合は Deny 優先、の 3 段で実効権限を決める。この順序はセキュリティ境界であり、設計書で擬似コードと真理値表を提示し、テストで固定する。

### 要件 P2-5: 権限に基づく API アクセス制御 〔foundation 要件 5-2〕

**ユーザーストーリー:** 利用者として、権限のないページを操作しようとしたら明確に拒否されたい。運用者として、権限のない操作が確実にブロックされると保証したい。

#### 受け入れ基準

1. WHEN 認証済み利用者が view 権限のないページを `GET /api/pages?path=` で取得しようとする THEN システム SHALL **403 Forbidden** を返す（存在は認めるが権限なし）。ただし要件 P2-7 の「存在秘匿」を選ぶ場合は 404 を返す（U-4 に記録）。
2. WHEN 認証済み利用者が edit 権限のないページを `PUT`/`DELETE /api/pages?path=` で更新・削除しようとする THEN システム SHALL **403 Forbidden** を返し、変更を行わない。
3. WHEN 認証済み利用者が新規ページを `POST /api/pages` で作成しようとする THEN システム SHALL 作成先 path の親階層に対する edit 権限（またはデフォルト編集許可）を要求し、無ければ **403** を返す。
4. WHEN リビジョン API（履歴一覧・差分・復元、要件 P2-8〜P2-11）を呼ぶ THEN システム SHALL 履歴一覧・差分には対象ページの view 権限を、復元には edit 権限を要求する。
5. THE 権限チェック SHALL サーバー側（DRF の permission クラスまたはビュー内判定）で行い、フロントの表示制御だけに依存しない。フロントの非表示は利便性のためで、セキュリティ境界はサーバーが担保する。
6. THE 権限エントリ管理 API（要件 P2-1-6）SHALL 対象ページの edit 権限を持つ主体または管理者のみに許可し、それ以外には 403 を返す。
7. THE アセット（`Folder`/`Asset`、`/api/folders`・`/api/assets` 系）SHALL 本フェーズでは **ページ権限の対象外**とし、フェーズ 1 と同じ挙動（`JANUS_REQUIRE_AUTH` に基づく認証のみ）を維持する。理由: アセットはページから独立した共有リソースで、ページ単位の閲覧権限とアセット配信権限の対応付け（1 アセットが複数ページから参照されうる）は本フェーズのスコープを超える。アセット権限は将来拡張として明示的に残す（U-5 に記録）。

### 要件 P2-6: 未認証アクセスと一覧での見え方 〔foundation 要件 4-2・5-2〕

**ユーザーストーリー:** 運用者として、未認証・無権限のアクセスがどう扱われるか、一覧に何が出るかを明確にしたい。そうすれば公開範囲を把握できる。

#### 受け入れ基準

1. WHEN 未認証の利用者が保護された API にアクセスする THEN システム SHALL **401 Unauthorized** を返す（認証を要求。フェーズ 1・`JANUS_REQUIRE_AUTH=true` の挙動を維持）。401（未認証）と 403（認証済みだが権限なし）を明確に区別する。
2. WHEN 認証済み利用者が子ページ一覧 `GET /api/pages/children?parent=` を取得する THEN システム SHALL **その利用者が view 権限を持つページのみ**を一覧に含める（権限のないページは一覧から除外する）。
3. WHEN ある親ページに view 権限が無いが、その子ページには明示的に view 権限が付与されている THEN システム SHALL 子ページ自体の閲覧・一覧表示は許可する（親が見えないことは子の閲覧を妨げない。権限は path 階層の継承だが、子の明示 Allow は親の非公開に優先する＝要件 P2-2-3 の具体性優先）。
4. WHEN 親が見えないために中間階層をたどれない THEN システム SHALL 一覧 API で、見える子ページを親の可視性に関わらず到達可能にする（例: 直接の深いパス指定での一覧取得、または見えるページだけを平坦に辿れる導線）。具体的な一覧提示方法は設計で確定するが、「親が非公開でも、許可された子に到達できる」ことを保証する。
5. THE 一覧の件数・path は view 権限のあるページに限って開示し、無権限ページの存在（path・タイトル）を一覧経由で推測させない。
6. THE フロントエンド SHALL 403/401 を受けた際、閲覧画面では「閲覧権限がありません」、未認証では `/login` 誘導、編集操作の 403 では「編集権限がありません」を表示し、無権限のページ内容・リビジョン本文を描画しない。

### 要件 P2-7: 存在秘匿ポリシー（403 と 404 の選択）

**ユーザーストーリー:** 運用者として、権限のないページの「存在」を無権限ユーザーに知られたくない場合がある。そうすれば秘匿性の高いページ構成を隠せる。

#### 受け入れ基準

1. THE システム SHALL 無権限ページへの閲覧要求に対する応答を「403（存在は認める）」または「404（存在を秘匿）」から選べるポリシー設定を持つ（環境変数。例 `JANUS_HIDE_FORBIDDEN=false`）。
2. THE 既定値 SHALL **403（存在を認める）**とする。理由: 挙動が直感的で、権限リクエストの導線（「アクセス権を依頼」等、将来）を設計しやすい。秘匿が必要な運用のみ 404 に切り替える。
3. WHEN `JANUS_HIDE_FORBIDDEN=true` THEN システム SHALL 無権限ページの単一取得・更新・削除で 404 を返し、一覧からも除外する（要件 P2-6-2 と一致。一覧は既に除外のため挙動は 403/404 で変わらない）。
4. THE edit 権限なしの書き込み（PUT/DELETE/POST）SHALL 存在秘匿ポリシーに関わらず、情報漏洩を避けるため **404 または 403 の応答本文に本文・メタ情報を含めない**。

### 要件 P2-8: リビジョンの記録 〔foundation 要件 6-1〕

**ユーザーストーリー:** 利用者として、ページを保存するたびにその時点の状態を履歴として残したい。そうすれば後から変遷を追い、復元できる。

#### 受け入れ基準

1. WHEN ページ本文が作成（`POST /api/pages`）または更新（`PUT /api/pages`）で保存される THEN システム SHALL その時点のリビジョン（本文の全文スナップショット・保存日時・編集者）を記録する。
2. THE リビジョン SHALL 対象ページ・本文（body の全文）・作成日時・編集者（`auth.User` への FK、`SET_NULL`）・（任意）タイトルを保持する。
3. THE 保存方式 SHALL **全文スナップショット**とする（差分保存ではない）。理由: foundation design 11 章で第一候補として記録済み。差分は表示時に計算する（要件 P2-10）。実装が単純で、個別リビジョンの独立復元・破損耐性に優れる。
4. WHEN ページ新規作成が成功する THEN システム SHALL 初回リビジョン（リビジョン番号 1 相当）を 1 件記録する。
5. THE `Page.body` SHALL 引き続き最新本文のキャッシュとして保持する（foundation design 3 章の想定どおり。既存の読み取り経路・テストを壊さない）。最新リビジョンの本文と `Page.body` は一致する。
6. THE リビジョン記録 SHALL ページ保存トランザクション内で原子的に行う。本文保存に成功しリビジョン記録に失敗した、またはその逆、という不整合を生じさせない。
7. THE リビジョンの作成 SHALL foundation の既存ページ CRUD API の **後方互換を保つ**（レスポンス形状の必須フィールドを削らない。リビジョン関連情報は追加フィールドまたは別エンドポイントで提供する）。

### 要件 P2-9: 重複リビジョンの抑制 〔foundation 要件 6-5〕

**ユーザーストーリー:** 利用者として、本文を変えていない保存で履歴が無駄に増えてほしくない。そうすれば履歴が意味のある変更だけで構成される。

#### 受け入れ基準

1. IF 保存操作時の本文（body）が直前（最新）リビジョンの本文と**完全一致**する THEN システム SHALL 新しいリビジョンを作成しない。
2. WHEN 本文は同一だがタイトルのみ変わる保存が行われた THEN システム SHALL リビジョンを作成するかどうかを設計で確定する（本書ではリビジョンは **本文の履歴**と位置づけ、**タイトルのみの変更ではリビジョンを作らず** `Page.title` のみ更新することを推奨。U-6 に記録）。
3. WHEN 重複により新規リビジョンを作成しなかった THEN システム SHALL ページ保存自体は成功として扱い（200）、`updated_at`/`updated_by` の更新有無を設計で確定する（本文不変時は履歴に残さないが、保存の事実として `updated_at` を更新するかを U-6 で判断）。
4. THE 重複判定 SHALL ページ単位で直前リビジョンとの比較に限定し、過去の任意リビジョンとの一致までは判定しない（コストと直感性のため）。

### 要件 P2-10: 履歴一覧と差分表示 〔foundation 要件 6-2・6-3〕

**ユーザーストーリー:** 利用者として、ページの変更履歴を新しい順に見て、任意の 2 時点の差分を確認したい。そうすれば何がいつ変わったか把握できる。

#### 受け入れ基準

1. WHEN 利用者が view 権限のあるページの履歴を要求する THEN システム SHALL リビジョン一覧を**新しい順**に返す（リビジョン ID/番号・日時・編集者・本文を含まない軽量メタを基本とし、本文は個別取得）。
2. THE 履歴一覧 API SHALL 件数が多い場合に備えページング（limit/offset またはカーソル）を提供する。
3. WHEN 利用者が 2 つのリビジョンを指定して差分を要求する THEN システム SHALL 行単位の差分（追加・削除・変更行）を返す。
4. THE 差分計算 SHALL **サーバー側で全文スナップショットから計算**することを基本とする（foundation design 11 章・要件 P2-8-3 と整合）。フロントは差分結果を表示する。差分アルゴリズムは行単位の標準的手法（Python 標準 `difflib` 相当）を用いる。
5. WHEN 指定されたリビジョンが対象ページに属さない、または存在しない THEN システム SHALL 404 を返す。
6. THE 差分 API SHALL 対象ページの view 権限を要求する（権限なしは 403/404、要件 P2-5・P2-7 に従う）。

### 要件 P2-11: リビジョンの復元 〔foundation 要件 6-4〕

**ユーザーストーリー:** 利用者として、過去のリビジョンを選んで現在の本文として復元したい。そうすれば誤編集を取り消せる。

#### 受け入れ基準

1. WHEN 利用者が edit 権限のあるページで過去リビジョンを指定して復元する THEN システム SHALL そのリビジョンの本文を**新しいリビジョンとして保存**し、`Page.body` を更新する（履歴は失わない。過去のリビジョンは消さない）。
2. THE 復元 SHALL 要件 P2-8 の通常保存経路を通り、復元で作られた最新リビジョンの編集者は復元操作者、日時は復元時刻とする。
3. IF 復元しようとした本文が現在の最新本文と完全一致する THEN システム SHALL 要件 P2-9 の重複抑制に従い新規リビジョンを作らず、復元を no-op 成功として扱う。
4. WHEN 指定リビジョンが存在しない/対象ページに属さない THEN システム SHALL 404 を返す。
5. THE 復元 SHALL edit 権限を要求する（権限なしは 403/404）。

### 要件 P2-12: 作者削除・ページ削除時のリビジョン挙動 〔foundation 要件 6 の境界〕

**ユーザーストーリー:** 運用者として、ユーザーやページを削除したときに履歴がどうなるか明確にしたい。そうすればデータの整合と監査性を保てる。

#### 受け入れ基準

1. WHEN リビジョンの編集者（`auth.User`）が削除される THEN システム SHALL リビジョン自体は保持し、編集者参照を null にする（`on_delete=SET_NULL`。foundation の `Page.created_by/updated_by` と同じ方針で整合）。履歴の本文・日時は失われない。
2. WHEN ページが削除される THEN システム SHALL そのページに紐づくリビジョンを**連動削除**する（`on_delete=CASCADE`）。理由: リビジョンはページ本文の履歴であり、ページ無き履歴は参照不能。コメント連動削除（foundation 要件 7-4）と同じ直感に合わせる。
3. THE ページ削除時のリビジョン連動削除 SHALL トランザクション内で原子的に行う。
4. 〔将来拡張・スコープ外〕 ページ削除の取り消し（ゴミ箱）やリビジョンのアーカイブは本フェーズのスコープ外とする。削除は現行どおり不可逆とし、必要なら将来拡張で検討する。

### 要件 P2-13: API 契約・StorageClient 拡張 〔foundation 要件 1〕

**ユーザーストーリー:** 開発者として、権限・リビジョン機能も統一 API 契約（`StorageClient`）の中で扱いたい。そうすればローカルモード（フェーズ 3）でも同契約で実装でき、二重開発を避けられる。

#### 受け入れ基準

1. THE システム SHALL 権限管理・リビジョン機能のクライアント操作を `StorageClient` 契約（`frontend/src/storage/types.ts`）に追加する。既存の `AuthClient`/`PageClient`/`AssetClient`/`SearchClient` の既存メソッドシグネチャは破壊しない（追加のみ）。
2. THE リビジョン契約 SHALL 「履歴一覧取得」「リビジョン本文取得」「2 リビジョンの差分取得」「復元」をカバーする（例 `PageClient` に `listRevisions`/`getRevision`/`diffRevisions`/`restoreRevision` を追加）。
3. THE 権限契約 SHALL 「ページの権限エントリ一覧」「付与」「取消/更新」「実効権限の問い合わせ（現在ユーザーが対象ページで view/edit 可能か）」をカバーする（例 新 `PermissionClient` インターフェースを定義し `StorageClient` に合成）。
4. THE 対応する REST エンドポイント SHALL foundation design 5 章の方式（`/api/` 配下、`?path=` または ID 指定、DRF）に揃える。追加エンドポイント例: `GET/POST/PATCH/DELETE /api/pages/permissions?path=`、`GET /api/pages/revisions?path=`、`GET /api/pages/revisions/<id>`、`GET /api/pages/revisions/diff?path=&from=&to=`、`POST /api/pages/revisions/restore`。最終的な URL/メソッドは設計で確定する。
5. THE 新規契約 SHALL ローカルモード（IndexedDB、フェーズ 3）でも同一契約で実装可能な抽象度に保つ（サーバー固有の実装詳細をインターフェースに漏らさない。foundation 要件 1-3 と整合）。

### 要件 P2-14: UI 統合 〔foundation 要件 2・5・6 の画面反映〕

**ユーザーストーリー:** 利用者として、ページ画面から履歴・差分・復元を操作し、運用者として権限をページ画面から設定したい。

#### 受け入れ基準

1. THE 閲覧画面（`PageViewPage`）SHALL 当該ページに view 権限がある場合に「履歴」導線を提供し、履歴一覧→差分→復元の操作を `StorageClient` 経由で行える。
2. THE 編集権限のない利用者 SHALL 編集・削除・復元・権限設定の UI を見えなくするか無効化する（ただしセキュリティ境界はサーバー、要件 P2-5-5）。
3. THE 権限設定 UI SHALL 対象ページの edit 権限を持つ主体または管理者に対して、ページ単位で主体（ユーザー/グループ）× 操作（view/edit）× 効果（allow/deny）を一覧・付与・取消できる最小 UI を提供する。
4. THE UI SHALL フェーズ 1 の軽量方針（重い UI フレームワークを入れない、素の CSS）を維持する（foundation 要件 13）。
5. WHEN 権限・リビジョン API が 401/403 を返す THEN UI SHALL 要件 P2-6-6 の表示規則に従う。

### 要件 P2-15: マイグレーションと後方互換

**ユーザーストーリー:** 運用者として、フェーズ 2 導入でフェーズ 1 の既存データ・API・テストが壊れないことを保証したい。

#### 受け入れ基準

1. THE 新規モデル（`PagePermission`・`Revision`）SHALL 追加マイグレーションで導入し、既存 `Page`/`Folder`/`Asset` の破壊的スキーマ変更を行わない（カラム追加が必要な場合も null 許容・デフォルトで既存行を保全）。
2. THE マイグレーション SHALL 既存ページデータを保持する。既存の各ページに対し、初回リビジョン（現在の `Page.body` を内容とする 1 件）を**バックフィル**するデータマイグレーションを提供する（履歴の起点を作る）。バックフィル時の編集者は `Page.updated_by`（null 可）、日時は `Page.updated_at` を用いる。
3. THE デフォルトポリシー初期値（要件 P2-3-2: 閲覧=許可・編集=許可）SHALL 既存の全認証ユーザーがこれまで通り全ページを読み書きできる状態を維持する（権限エントリを設定するまで挙動が変わらない）。
4. THE 既存のフェーズ 1 テスト（`tests_auth.py`・`tests_pages.py`・`tests_assets.py`・`tests_integration.py` 等）SHALL 本フェーズ導入後も合格し続ける。デフォルトポリシーが既定のままなら既存テストの期待値（201/200/401/409/404）は不変であることを前提とする。
5. WHERE 既存テストの期待挙動を変える必要が生じた場合 THE 変更 SHALL 「foundation を変更するのか phase2 で追加するのか」を設計書で明記し、フェーズ 1 の完了判定（既存の受入基準）を覆さない範囲に限定する。

### 要件 P2-16: データベース移植性（SQLite 必須・PostgreSQL 将来） 〔foundation 要件 12-2〕

**ユーザーストーリー:** 運用者として、当面は SQLite で動けばよいが、将来 PostgreSQL に移行する余地を残したい。

#### 受け入れ基準

1. THE 権限・リビジョンのスキーマ・制約・クエリ SHALL **SQLite 上で成立**することを本フェーズの必須条件とする（ユーザー方針: PostgreSQL 対応は後回しでよい）。
2. THE スキーマ・クエリ SHALL PostgreSQL への将来移行を阻害しない範囲に留める（SQLite 固有機能に依存した権限判定・差分計算を避け、Django ORM の標準機能で表現する）。階層継承の解決は path 文字列処理と ORM クエリ（`startswith` 等）で行い、DB 固有の再帰 CTE 等に依存しない。
3. THE 実効権限の計算 SHALL アプリケーション層（Python）で合成することを基本とし、DB 方言差の影響を最小化する。性能上の最適化（インデックス等）は SQLite/PostgreSQL 双方で有効な範囲で行う。

## 非機能要件

1. **セキュリティ境界**: すべての閲覧・編集可否判定の最終決定はサーバー側で行う。フロントの表示制御は補助に過ぎない（要件 P2-5-5）。401/403/404 の使い分けを一貫させる（要件 P2-6-1・P2-7）。
2. **後方互換**: フェーズ 1 の API 契約・テスト・既定挙動を破壊しない（要件 P2-15）。
3. **軽量性**: 権限・リビジョンの追加で foundation 要件 13（軽量・最小依存）を損なわない。差分は Python 標準ライブラリで計算し、重い依存を追加しない。追加の UI フレームワークを入れない。
4. **移植性**: SQLite で成立し、PostgreSQL 移行を阻害しない（要件 P2-16）。
5. **監査性**: リビジョンは編集者・日時を保持し、作者削除後も本文・日時を失わない（要件 P2-12-1、foundation 要件 4-5 の操作者記録と整合）。
6. **性能**: 階層継承・グループ合成の権限計算が、一覧 API（`children`）で N ページ分呼ばれても実用的な応答時間に収まるよう、祖先権限エントリの一括取得・キャッシュを設計で考慮する（詳細最適化はスコープを限定）。

## 受け入れ基準（統合・テスト観点のサマリ）

本フェーズ完了時、以下がテストで検証可能であること（番号は検証項目）。

1. 認証済みだが view 権限のないページの `GET /api/pages?path=` が 403（既定）または 404（`JANUS_HIDE_FORBIDDEN=true`）を返す。
2. 未認証アクセスが 401 を返し、401 と 403 が区別される。
3. edit 権限のないページの `PUT`/`DELETE` が 403 を返し、本文が変化しない。
4. 親に view 権限が無く子に明示 Allow があるとき、子ページを閲覧・一覧取得できる（要件 P2-6-3）。
5. 子ページ一覧 `children` が view 権限のあるページのみを返し、無権限ページの存在を漏らさない。
6. 階層継承で、より近い祖先/自身の設定が祖先より優先され、同一レベルでは Deny が勝つ（真理値表どおり）。
7. user 直接付与がグループ経由付与より（同一レベルで）優先される。
8. `is_superuser` が権限エントリに関わらず全ページを読み書きできる。
9. デフォルトポリシー既定（閲覧=許可・編集=許可）で、権限エントリ未設定ページがフェーズ 1 と同じく全認証ユーザーに読み書き可能。
10. ページ保存で全文スナップショットのリビジョンが 1 件記録され、`Page.body` が最新リビジョンと一致する。
11. 本文不変の保存でリビジョンが増えない（重複抑制）。
12. 新規作成で初回リビジョンが 1 件できる。
13. 履歴一覧が新しい順・ページング付きで返る。
14. 2 リビジョンの行単位差分が返る（存在しないリビジョン指定は 404）。
15. 復元が過去本文を新リビジョンとして保存し、過去リビジョンを消さない。
16. 復元時に本文が現在と一致すればリビジョンを増やさない（no-op 成功）。
17. 編集者ユーザー削除後もリビジョンが残り、編集者が null になる。
18. ページ削除でそのページのリビジョンが連動削除される。
19. 権限エントリ管理 API が edit 権限者/管理者のみに許され、他は 403。
20. アセット API（`/api/folders`・`/api/assets`）がページ権限の影響を受けず、フェーズ 1 挙動を維持する。
21. 既存フェーズ 1 テスト（auth/pages/assets/integration）が全て合格し続ける。
22. 既存ページへの初回リビジョン・バックフィルがマイグレーションで作成される。
23. 全スキーマ・クエリが SQLite で成立する。

## foundation との関係（重複・矛盾の扱い）

- **要件 5/6 の具体化**: 本書 P2-1〜P2-14 は foundation 要件 5・6 を実装レベルに具体化したもの。foundation 要件書は変更せず、phase2 で詳細を追加する。
- **デフォルトポリシー・存在秘匿**: foundation には明記が無い既定挙動（P2-3・P2-7）を phase2 で新規に定義する。既定値はフェーズ 1 挙動（全認証ユーザー読み書き可）を保つよう選び、既存テストを壊さない。
- **`Page` スキーマ**: 親子 FK を追加せず path 文字列で階層継承する方針で、foundation design 3 章「`Page.body` は最新キャッシュ」「Revision 追加時も body を残す」という将来想定に沿う。`Page` への破壊的変更はしない。
- **ユーザー/グループ**: foundation 要件 4-6「Django 標準認証機構を基盤」に従い、`auth.User`/`auth.Group` をそのまま主体に用いる。
- **リビジョン保存方式**: foundation design 11 章の第一候補「全文スナップショット + 表示時差分計算」を採用（P2-8-3・P2-10-4）。
- **認証移行**: foundation design 5 章のセキュリティ移行方針（Token→Cookie セッション等）は将来拡張のまま。phase2 は Token 認証の上に権限レイヤを足すだけで、`AuthClient` 契約・画面を不変に保つ。
- **アセット独立性**: foundation 要件 14 の「アセットはページ従属でない独立リソース」を尊重し、ページ権限をアセットに波及させない（P2-5-7）。これは矛盾ではなく、アセット権限を別課題として将来に残す明示的判断。

## ユーザー判断が必要な未確定事項（設計レビューで確認）

推奨案を選び実装を進めるが、以下はセキュリティ・運用に影響するため設計レビューで最終確認する。合理的な推奨案と理由を併記する。

- **U-1（権限モデルの実装基盤）**: 独自 `PagePermission` モデル（推奨）か、django-guardian 等のオブジェクト権限ライブラリか。推奨理由: 階層継承・Allow/Deny・デフォルトポリシーという Janus 固有合成を素直に表現でき、依存を増やさず軽量方針（foundation 要件 13）に合う。**セキュリティ境界に関わるため要確認。**
- **U-2（権限エントリの付与対象）**: 実在ページの path のみに権限を付与可能とするか、任意の path プレフィックス（仮想ノード）にも付与可能とするか。推奨: 仮想ノード許容（`/docs` ページが無くても `/docs` 配下に継承させられる）。理由: 階層単位制御（foundation 要件 5-1「または階層単位」）を自然に満たす。
- **U-3（グループ/ユーザー管理手段）**: 本フェーズは Django admin + 最小 API に留める（推奨）。本格的な管理 UI はスコープ外。
- **U-4（無権限時の 403/404）**: 既定 403（存在を認める、推奨）。秘匿運用のみ `JANUS_HIDE_FORBIDDEN=true` で 404。**公開範囲の秘匿性に関わるため要確認。**
- **U-5（アセット権限）**: 本フェーズはアセットをページ権限の対象外とする（推奨）。1 アセットが複数ページから参照されうるため、ページ閲覧権限とアセット配信権限の対応付けは将来の専用課題とする。**無権限ユーザーがアセット直リンク（`/api/assets/<id>/file`）で画像を取得しうる点はセキュリティ上の明示事項として要確認。**
- **U-6（本文不変・タイトルのみ変更時の扱い）**: 本文不変ならリビジョンを作らない（推奨）。タイトルのみ変更は `Page.title` のみ更新しリビジョンを作らない（推奨）。本文不変保存時の `updated_at` 更新有無は設計で確定。
- **U-7（デフォルトポリシー既定値）**: 閲覧=許可・編集=許可（推奨。フェーズ 1 後方互換）。「原則非公開」を既定にしたい運用方針があるなら要確認。**既定を非公開に倒すとフェーズ 1 の挙動と既存テスト前提が変わるため要確認。**
