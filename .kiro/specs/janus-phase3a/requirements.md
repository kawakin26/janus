# Janus フェーズ 3a 要件定義書（サーバーモードのコンテンツ機能）

## 概要

本書は Janus フェーズ 3 のうち **3a（サーバーモード側のコンテンツ機能）** の要件を定義する。フェーズ 3 はユーザー合意により **3a（サーバー側機能）** と **3b（ローカルモード = PWA + IndexedDB + オフライン + 端末カメラ）** に分割し、本書は 3a のみを扱う。

フェーズ 1（janus-foundation、サーバーモード基盤・独立アセットライブラリ・地図記法表示）とフェーズ 2（janus-phase2、ページ権限・リビジョン）は完了・コミット済みであり、本フェーズはそれらの上に積み上げる。3a で対象とする foundation 要件は次のとおり。

- **要件 7**: コメント / メモ機能。
- **要件 8**: CAD 変換（.jww を主・.dxf も対象、→ SVG、アセットライブラリへ登録、向き 0/90/180/270 度の焼き込み、失敗時フォールバック、元 CAD は保持しない）。**変換はブラウザ（フロントエンド）で行う**（サーバーは変換に関与しない）。
- **要件 9**: 描画機能（draw.io / diagrams.net を**セルフホスト同梱**で埋め込み、図を XML（mxGraph）として保持、閲覧時レンダリング、将来の手動エクスポート/インポート同期を阻害しない形式）。
- **要件 3-4**: 地図 GUI 編集（編集画面で GUI によりマーカーを配置し `:::custom-map` 記法を生成/更新）。
- **要件 3-5**: 現場写真添付（マーカーの参考写真）。**ただしサーバーモードの写真アップロード・アセット登録・記法への紐付けのみを 3a 対象とし、端末カメラ API 連携（撮影）は 3b/将来に送る**（本書で明示的に分割する）。

本フェーズは要件定義のみを扱う。設計・実装・コミットは後続ステップで行い、**本書の段階ではアプリケーションコード（backend/frontend）を一切変更しない**。

### フェーズ 3a のスコープ境界（最重要）

本書の全要件に通底する境界を先に明記する。詳細は各要件・末尾「スコープ外」に記す。

- **サーバーモードのみ（ただし CAD 変換・draw.io はローカルでも成立する設計）**。ローカルモード（IndexedDB・オフライン・端末カメラ・PWA）は **3b**（foundation 要件 10）。本フェーズは「同一 `StorageClient` 契約（foundation 要件 1）を 3b でも満たせる抽象度」を保つことまでを担保し、ローカル実装はしない。ただし後述のとおり **CAD 変換はブラウザ内で完結**し、**draw.io はセルフホスト同梱**でオフライン編集可能なため、これら 2 機能は 3b でも追加実装なしで再利用できる（3a で作る成果が 3b を阻害しない）。
- **CAD 変換はブラウザ（フロントエンド）で完結する**。サーバーは変換に一切関与しない（CAD 変換用の Django エンドポイント・サーバー変換ライブラリを設けない）。ユーザーの主フォーマットは JWW であり、JWW→SVG 変換資産（`ezjww`/WASM）はブラウザ資産であるため、変換をブラウザで行うことで (a) JWW/DXF 資産を直接再利用でき、(b) ローカルモード（3b）でも端末内で変換が完結し「軽量・ローカル完結」（foundation 要件 13・8-3）に合致し、(c) サーバーを軽量に保てる。変換後の SVG は既存 `AssetClient.uploadAsset` で独立アセットライブラリへ登録する。**foundation 要件 8-3 の「ローカル = 事前変換済み画像/SVG の取り込み」は、ブラウザ変換により「事前変換不要（端末内で直接変換）」へ改善される**（この整合は設計書で明記する）。
- **現場写真の「撮影（カメラ起動）」は 3a 対象外**。3a は「既存ファイルを選んでアップロード → アセット登録 → マーカーの参考写真として記法に紐付け」までを対象とする。端末カメラからの直接取り込みは 3b（foundation 要件 10-4）。
- **フェーズ 1/2 を非破壊**。既存の `Page`/`Folder`/`Asset`/`PagePermission`/`Revision` スキーマ、既存 REST エンドポイント・レスポンス必須フィールド、既存の約 145 件のバックエンドテスト・約 132 件のフロントテストを壊さない。新規モデル・追加フィールド・別エンドポイント・追加マイグレーションで積み上げる。
- **地図記法仕様（`:::custom-map`）を非破壊**。GUI 編集は既存パーサ（`parse-map.ts`）が読める記法だけを生成/更新する。コンテナ属性（`folder`/`cx`/`cy`/`scale`/`rotate`/`link`/`restore`/`pinSize`/`labelSize`）、マーカー（`x`/`y`/`label`/`desc`/`color`）、写真（`filename:`/`file:`/`aliasname:`/`alias:` と `desc`）の意味を変えない。

### 用語（本フェーズで用いる定義）

- **コメント**: ページに紐づく注記/メモ。本文・日時・（サーバーモードでは）投稿者を持つ。ページ本文（リビジョン対象）とは独立したレコード。
- **CAD 変換**: **ブラウザ（フロントエンド）内で** .jww（主）/.dxf を SVG へ変換し、変換後 SVG を既存 `AssetClient.uploadAsset` で独立アセットライブラリ（foundation 要件 14）へ登録する処理。変換はサーバーを介さない。元 CAD ファイルは保持しない（アセットに残るのは変換後 SVG のみ）。
- **向き焼き込み**: 変換時に 0/90/180/270 度の回転を SVG の内容そのものに適用して登録すること（記法 `rotate` による表示時回転とは別。下記 要件 3A-2 で両者の関係を定義）。
- **描画**: draw.io（diagrams.net）形式の図。mxGraph XML で保持する。
- **地図 GUI 編集**: 編集画面でマーカーの配置・ラベル/色/説明・参考写真を GUI 操作で編集し、`:::custom-map` 記法を生成/更新する機能。
- **記法シリアライズ**: GUI の編集状態（マップ画像参照・マーカー群・写真群・コンテナ属性）から `:::custom-map` の Markdown テキストを組み立てること。

### 前提となる現状（フェーズ 1/2 の確認結果・コード実査）

本書は以下の実コードを読んで前提を確定した。

- **ページ保存の単一経路**: `backend/api/services.py` の `save_page_body(page_or_path, *, title, body, author)` が作成/更新/復元の 3 入口を 1 トランザクションに集約し、本文スナップショット（`Revision`）・連番採番・本文不変時の重複抑制・`Page.body` 更新を所有する。本文を変える操作はすべてこの関数を通す（不変条件: 最新リビジョン body == `Page.body`）。
- **権限ゲート**: `backend/api/permissions.py` の `require_page_permission(request, path, action)`（許可=None / 拒否=403 既定・404 秘匿時）と `check_permission`/`compute_view_edit`。view/edit の実効権限は `permissions_logic.effective_permission`（階層継承 → 具体性 → Deny 優先、`is_superuser` バイパス）が純粋関数で決める。`JANUS_DEFAULT_PAGE_VIEW`/`JANUS_DEFAULT_PAGE_EDIT`/`JANUS_HIDE_FORBIDDEN` と `JANUS_REQUIRE_AUTH` で既定挙動を切替。
- **アセットは独立リソース**: `Folder`/`Asset`（`backend/api/models.py`）。`/api/folders`・`/api/assets`（`AssetListCreateView`/`AssetMoveView`/`AssetFileView`）。アップロードは multipart（`file`、任意 `alias`）、`(folder, filename)`/`(folder, alias)` フォルダ内一意、重複は 409。物理はフラット保存（UUID 名）、論理階層は `Folder` FK が持つ。**フェーズ 2 でアセットはページ権限の対象外**（`JANUS_REQUIRE_AUTH` の認証のみ、P2-5-7、未解決事項 U-5）。
- **地図記法**: フロント `frontend/src/markdown/custom-map/`。`remark-custom-map.ts` が `:::custom-map` を `buildMapData`（`parse-map.ts`）で `MapData` 化し `MarkdownRenderer` が `CustomMapViewer` を描画する。`AssetRef`（基準フォルダ + 出現順の filename/alias 指定子）で `resolveAssetUrl` が解決。表示（パン/ズーム/90 度回転/最小化/写真ポップアップ）は実装済み。**GUI 編集・CAD 変換・写真アップロードは未実装（フェーズ 3 と明記されている）**。
- **編集画面**: `frontend/src/pages/PageEditPage.tsx` は title + body（Markdown textarea）の素朴なフォーム。保存は `createPage`/`updatePage` 経由。
- **StorageClient 契約**: `frontend/src/storage/types.ts`。`AuthClient`/`PageClient`（リビジョン操作含む）/`AssetClient`（`listFolders`/`createFolder`/`listAssets`/`uploadAsset`/`moveAsset`/`getAssetFileUrl`/`releaseAssetFileUrl`/`resolveAssetUrl`）/`SearchClient`/`PermissionClient`。
- **コメント・CAD 変換・draw.io はコード・モデル・マイグレーションのいずれにも未着手**（migrations は 0004 まで＝権限/リビジョン + 初回リビジョンバックフィル）。
- **検証環境**: SQLite。`backend/../.venv/bin/python`。既存約 145（backend）/ 約 132（frontend）テストを回帰させない。

## 要件

### 要件 3A-C: コメント / メモ機能 〔foundation 要件 7〕

**ユーザーストーリー:** 利用者として、ページに注記やメモを残し、他の利用者（や後の自分）が参照できるようにしたい。そうすれば本文を書き換えずに補足情報や覚書を蓄積できる。

#### 受け入れ基準

1. WHEN 認証済み利用者がページにコメントを追加する THEN システム SHALL コメント本文・作成日時・投稿者（`auth.User`）を当該ページに紐付けて保存し、作成したコメントを返す。
2. WHEN 利用者がページを閲覧（取得）する THEN システム SHALL そのページのコメント一覧を取得できる手段を提供する（本文・日時・投稿者・一意 ID を含む）。一覧の順序は作成日時昇順（古い順）を既定とする。
3. WHEN 投稿者が自分のコメントを編集する THEN システム SHALL 本文を更新し、更新日時を記録する（投稿者・作成日時は不変）。
4. WHEN 投稿者が自分のコメントを削除する THEN システム SHALL そのコメントを削除する。
5. WHEN ページが削除される THEN システム SHALL そのページに紐づくコメントを連動削除する（`on_delete=CASCADE`、foundation 要件 7-4、phase2 の `Revision` 連動削除と同じ直感）。
6. WHEN コメント投稿者（`auth.User`）が削除される THEN システム SHALL コメント本体は保持し投稿者参照を null 化する（`on_delete=SET_NULL`、`Page.created_by`・`Revision.author` と同方針。監査性のため本文・日時を失わない）。
7. THE コメント本文 SHALL 必須・文字列・最大長を定める（上限は設計で確定、空文字・空白のみは 400 で拒否）。本文は保存時にそのまま保持し、表示側のサニタイズに依存しない（コメントは Markdown レンダリングの対象にするか否かを設計で確定するが、既定はプレーンテキスト扱いとし XSS 経路を作らない）。
8. THE コメントの保存・編集・削除 SHALL `Page.body`（本文）やリビジョンに影響を与えない（コメントはリビジョン対象外。本文の履歴とコメントは独立）。

#### 権限との関係（セキュリティ境界、下記「権限との関係」節で統合）

9. WHEN 利用者がページのコメント一覧を取得する THEN システム SHALL 対象ページの **view 権限**を要求する（権限なしは 403／秘匿時 404、phase2 P2-5・P2-7 に従う）。
10. WHEN 利用者がコメントを投稿する THEN システム SHALL 対象ページの **view 権限**を要求する（閲覧できる利用者はコメントを残せる、を既定とする。U-3A-1 参照）。
11. WHEN 利用者がコメントを編集・削除する THEN システム SHALL **投稿者本人**、または対象ページの **edit 権限を持つ主体**、または **管理者（`is_superuser`）** のみに許可し、それ以外には 403 を返す（foundation 要件 7-3「自分のコメント」を基本に、モデレーションのため edit 権限者/管理者も可とする）。

### 要件 3A-CAD: CAD 変換（.jww/.dxf → SVG のアセット登録、ブラウザ変換） 〔foundation 要件 8〕

**ユーザーストーリー:** 利用者として、CAD 図面（主に .jww、.dxf も）を選ぶだけで地図として使える SVG にしたい。そうすれば手動で画像化せずに図面を地図記法の背景として扱える。ネットワークに依存せず端末上で完結すると、ローカルモードでも同じ操作で使える。

#### 受け入れ基準

1. WHEN 利用者が CAD ファイル（.jww または .dxf）を選んで変換登録する THEN システム SHALL **ブラウザ（フロントエンド）内で** SVG へ変換し、変換後 SVG を既存 `AssetClient.uploadAsset` で独立アセットライブラリ（foundation 要件 14）に **1 件のアセットとして登録**し、登録結果（通常の `Asset` と同一形状）を返す。**サーバーは変換に一切関与しない**（CAD 変換専用の Django エンドポイント・サーバー変換ライブラリを設けない。SVG 登録は既存のアセットアップロード経路をそのまま使う）。
2. WHEN CAD をアセット登録する THEN システム SHALL 向き（0/90/180/270 度）の指定を**変換時に**受け取り、その回転を **SVG の内容に焼き込んで**（SVG の `viewBox`/座標変換に反映して）登録できる（foundation 要件 8-2）。向き未指定時は 0 度とする。向きの焼き込みはブラウザ変換の中で行い、登録前に完了する。
3. THE 登録される SVG アセット SHALL アップロード先フォルダ・filename・任意 alias を通常の画像アップロードと同じ規則（フォルダ内一意、重複 409）で扱う（既存 `uploadAsset` の規則をそのまま使う）。登録後は地図記法から `filename:`/`alias:` で参照できる（foundation 要件 14-9〜14-12）。filename は SVG 拡張子（`.svg`）に正規化する（元の `.jww`/`.dxf` 名から拡張子を置換する規則を設計で確定）。
4. THE 元の CAD ファイル SHALL 変換後に保持しない（foundation 要件 8-1。アセットライブラリに残るのは変換後 SVG のみ。元 CAD はブラウザのメモリ上で変換に使うだけでアップロードしない）。
5. IF 変換に失敗する（未対応ファイル・破損 CAD・エンティティ数が上限超過・WASM 読み込み不可等）THEN システム SHALL 変換を**失敗として利用者に明確に通知**し（アセットを登録しない）、**通常の画像/SVG アップロード経路（`uploadAsset`）へ案内する**フロントエンドのエラー表示を行う（foundation 要件 8-4）。変換はアセット登録より前にブラウザ内で行うため、失敗時にアセットは一切登録されず副作用（孤児）も残らない。サーバーが関与しないため、失敗は HTTP ステータスではなく**フロントエンドのエラー提示**で表現する（文言・導線は設計で確定）。
6. THE CAD 変換 SHALL アセットライブラリ登録の一手段として位置づけ、**変換ロジックをフロントエンド内のユーティリティとして実装する**（foundation 要件 8-5）。JWW は `ezjww`（WASM）、DXF は `dxf-parser` + `iconv-lite`（Shift-JIS/UTF-8 判定）を用い、座標変換・向き焼き込み・色/線種・境界/viewBox の各ロジックを参考実装（`jww-to-svg.js`/`dxf-to-svg.js`）から移植する。変換器の設定値（色・線種・`maxEntities` 等、参考実装の `config.js` 相当）は Janus 側に定義する。変換は `StorageClient`/`AssetClient` 契約には載せず（契約の追加なし）、SVG 登録のみ既存 `uploadAsset` を使う（下記 8）。
7. THE 3a の変換対象 SHALL **.jww（主）と .dxf** とする。両者ともブラウザ内で変換する。未対応の拡張子・内容は基準 5 のフォールバック（失敗通知 + 通常アップロード案内）に落とす。
8. THE CAD 変換の **SVG 登録** SHALL 既存 `AssetClient.uploadAsset`（フォルダ指定・任意 alias・フォルダ内一意・重複 409）をそのまま用いる（新しいアップロード契約・エンドポイントを増やさない）。**CAD→SVG 変換そのものは `StorageClient` 契約に載せず、フロントエンド内のクライアント内ユーティリティ**として実装する（サーバー非関与のため契約の抽象に変換を漏らさない）。ローカルモード（3b）はこの変換ユーティリティと `uploadAsset`（ローカル実装）をそのまま再利用して端末内で完結でき、foundation 要件 8-3 の「事前変換済み取り込み」が「端末内直接変換」へ改善される。

#### 性能・応答性（ユーザー懸念: ブラウザがハングしないこと）

9. 図面登録は低頻度の操作だが、THE ブラウザ変換 SHALL UI をハングさせない配慮を持つ: **(a) 入力ファイルサイズの上限**、**(b) エンティティ数の上限**（参考実装 `maxEntities` 相当。パース直後に上限超過を拒否）、**(c) 変換中の明示的なローディング表示**、**(d) 可能なら Web Worker 上での変換実行**（UI スレッドをブロックしない）を備える。重い図面は上限で安全に拒否し、基準 5 のフォールバックに落とす。具体の上限値・Worker 採用可否は設計で確定する。

#### セキュリティ

10. THE 変換で生成した SVG SHALL 既存のアセット SVG 配信/表示ポリシー（foundation の XSS 配慮）に従う。既存の地図表示が SVG を `<img src>`（Blob URL）で描画しスクリプト実行コンテキストに置かないことを維持し、外部由来 SVG を信頼しない姿勢（画像的扱い）を崩さない。変換ユーティリティは `<script>`/`foreignObject` を含まないベクタ図形のみを出力する。

#### 権限との関係

11. WHEN 利用者が変換後 SVG を登録する THEN システム SHALL **フェーズ 2 と同じアセット権限ポリシー**（アセット操作はページ権限の対象外、`JANUS_REQUIRE_AUTH` に基づく認証のみ、P2-5-7）を適用する（登録は既存 `uploadAsset` 経由のため既存ポリシーがそのまま効く）。本フェーズでアセット単位の権限を新設しない（U-3A-2 参照）。

### 要件 3A-DRAW: 描画機能（draw.io 埋め込み） 〔foundation 要件 9〕

**ユーザーストーリー:** 利用者として、ページ内に draw.io で図を作図し、閲覧時に図として表示したい。そうすれば文章だけでは伝わらない構造を図示できる。

#### 受け入れ基準

1. WHEN 利用者が編集画面で描画を作成/編集する THEN システム SHALL draw.io（diagrams.net）の**セルフホスト同梱**エディタを提供し、作図結果を **mxGraph XML** として取得する（foundation 要件 9-1）。実行時に外部ドメイン（公開 `embed.diagrams.net` 等）へ接続しない。
2. WHEN 利用者が描画を保存する THEN システム SHALL その XML を**ページ本文（Markdown）内に保持**し、保存は既存の `save_page_body` 単一経路を通す（本文変更としてリビジョンに記録される、phase2 P2-8。描画の変更履歴もページ履歴として追える）。
3. THE 描画 XML の本文内での保持形式 SHALL **Markdown コードフェンス方式か専用ディレクティブ方式のいずれかを設計で 1 つ選び確定する**（foundation design 11 章の 2 案）。選定要件: (a) 既存 Markdown レンダラ（`MarkdownRenderer`）・既存 `:::custom-map` 処理（`remark-directive` 系）と共存し壊さない、(b) 生 HTML 無効（rehype-raw 不採用）の現方針を維持し XSS 経路を作らない、(c) 1 ページに複数の描画を持てる、(d) 将来の手動エクスポート/インポート同期（B 案）を阻害しない自己完結のテキスト形式（基準 7）。
4. WHEN 描画を含むページを閲覧する THEN システム SHALL その XML から図をレンダリング表示する（foundation 要件 9-2）。レンダリング手段（draw.io ビューア埋め込み / XML→SVG 変換 / 画像化のいずれか）は設計で確定するが、閲覧は編集と同様サーバープロセスに依存せず**フロントで完結**できることを優先する（foundation 設計方針「レンダリングはフロント」との整合、3b での再利用性）。
5. THE 描画データ SHALL 本文テキストとして自己完結し、別アセットや外部サービスへの実行時依存を持たない形式で保持する（foundation 要件 9-4。将来の同期・移植を阻害しない。draw.io エディタ自体の読み込み元は設計で確定するが、保存データは XML テキストのみで完結する）。
6. THE draw.io エディタの提供方式 SHALL **セルフホスト同梱**（diagrams.net コア Apache-2.0 を同梱・自前配信）とする。公開 `embed.diagrams.net` は採用しない。これにより編集・閲覧いずれも**実行時に外部ドメインへ依存せず**、オフライン（3b）でも作図が成立する。同梱配布物（`drawio-webapp` 等）と Vite での配信方法、bundle サイズ影響は設計で確定する。3a はサーバーモードでの編集・閲覧を主対象とするが、セルフホスト同梱によりローカルモード（3b）での作図も追加実装なしで成立しうる（3a の成果が 3b を阻害しない）。
7. THE 描画の保存・閲覧 SHALL ページ本文を介するため、既存のページ view/edit 権限（phase2）がそのまま適用される（別途の権限を新設しない）。

### 要件 3A-MAP: 地図 GUI 編集 〔foundation 要件 3-4〕

**ユーザーストーリー:** 利用者として、編集画面で地図画像の上をクリックしてマーカーを置き、ラベル・色・説明・参考写真を GUI で設定したい。そうすれば `:::custom-map` 記法を手書きせずに地図を作成/更新できる。

#### 受け入れ基準

1. WHEN 利用者が編集画面で地図を新規作成/編集する THEN システム SHALL GUI でマップ画像（アセット）を選択し、画像上の位置指定でマーカーを配置・移動・削除し、各マーカーのラベル・色・説明・座標（`x`/`y`）を編集できる（foundation 要件 3-4）。
2. WHEN GUI 編集の結果を保存する THEN システム SHALL 編集状態から `:::custom-map` 記法テキストを生成/更新し、既存パーサ（`parse-map.ts` の `buildMapData`）が同一の `MapData` に読み戻せる記法だけを出力する（往復保存の無損失性: GUI → 記法 → パース で意味が保たれる）。
3. THE 生成する記法 SHALL 既存のコンテナ属性（基準フォルダ `folder`、`cx`/`cy`/`scale`/`rotate`/`link`/`restore`/`pinSize`/`labelSize`）、マーカー箇条書き（`x`/`y`/`label`/`desc`/`color`）、写真の子リスト（`filename:`/`file:`/`aliasname:`/`alias:` と `desc`）のみを用い、属性名・意味・既定値・クランプ範囲（`parse-map.ts`/`map-utils.ts` の定義）を変えない。
4. THE マップ画像・写真の参照 SHALL 独立アセットライブラリの参照指定子で生成する（foundation 要件 14-9〜14-12）。GUI は参照を**二重指定しない**（1 参照につき filename か alias の一方のみを出力する。foundation 要件 14-11 の「二重指定は避ける」に従う）。基準フォルダは `folder` 属性として出力し、個別参照にスラッシュを含めてフォルダを上書きするかは設計で確定する（既定は基準フォルダ運用）。
5. WHEN GUI 編集で生成した記法を含むページを保存する THEN システム SHALL 既存の `save_page_body` 単一経路（ページ本文更新）を通し、変更をリビジョンに記録する（phase2 P2-8。地図の変更履歴がページ履歴として追える）。地図 GUI 編集専用の保存経路・エンドポイントは設けない（本文の一部として保存する）。
6. THE 記法シリアライズ SHALL 特殊文字（引用符・バックスラッシュ・改行・`|`・`/`・コロン等）を既存パーサの読み取り規則（`parse-map.ts` の `readAttrValue`/`unescapeAttr`、`|` は改行表現）と整合するようエスケープ/整形する。GUI 入力値がパーサを壊さない（例: ラベルに `"` を含んでも往復で保たれる）ことを保証する。
7. THE GUI 編集 SHALL 既存の記法を含むページを編集する場合、既存記法をパースして GUI 状態に取り込み、未知/手書きの追加記述を**不用意に破壊しない**方針を設計で確定する（最低限、GUI が扱うブロックの外にある本文は保持する。1 ブロックの往復は無損失、GUI 対象外の属性は保持する）。
8. THE 地図 GUI 編集機能 SHALL 既存の閲覧用 `CustomMapViewer`・パーサを壊さない（表示は不変、追加は編集 UI のみ）。本フェーズは「GUI 編集で記法を生成/更新する」ことまでを対象とし、新規ページ作成フロー内での地図初期設定の作り込みは最小でよい。

### 要件 3A-PHOTO: 現場写真添付（サーバーモードのアップロード・紐付け） 〔foundation 要件 3-5〕

**ユーザーストーリー:** 利用者として、現場で用意した写真をマーカーの参考写真として添付したい。そうすればマーカーをクリックしたときに現場の状況を写真で確認できる。

#### 受け入れ基準

1. WHEN 利用者が地図 GUI 編集でマーカーに参考写真を追加する THEN システム SHALL **端末上の既存画像ファイルを選択してアップロード**し、独立アセットライブラリへ登録し（foundation 要件 14-6）、その参照を当該マーカーの写真子リスト（`filename:`/`alias:` + `desc`）として記法に紐付ける。
2. THE アップロード SHALL 既存の `AssetClient.uploadAsset`（フォルダ指定・任意 alias・フォルダ内一意・重複 409）を用い、新規のアップロード経路を増やさない（通常画像と同じアセット登録。CAD のみ変換経路が別＝要件 3A-CAD）。
3. WHEN 写真を紐付けた地図を保存する THEN システム SHALL 要件 3A-MAP-5 と同様に `save_page_body` 経由でページ本文として保存する（写真参照は記法の一部）。
4. THE 写真参照の解決・表示 SHALL 既存の `resolveAssetUrl`・`CustomMapViewer` の写真ポップアップをそのまま用いる（表示側は不変）。
5. 〔3a スコープ外・3b へ〕 THE **端末カメラ API による撮影（カメラ起動）** SHALL 本フェーズの対象外とする（foundation 要件 3-5・10-4）。3a は「既存ファイルの選択アップロード」までで、撮影からの直接取り込みは **3b（ローカルモード）** で扱う。この分割を UI/契約上も意識し、3a の写真添付は撮影 UI を前提にしない。
6. THE 写真アップロード・紐付け SHALL アセット権限ポリシー（アセットはページ権限の対象外、P2-5-7）に従う（要件 3A-CAD-9 と同じ。U-3A-2）。

## 権限との関係（セキュリティ境界・横断要件）

本フェーズの新機能はすべて「ページに対する操作」か「アセットに対する操作」のいずれかであり、既存のフェーズ 2 権限モデルに次のとおり対応づける。既存の権限判定（`require_page_permission`・`effective_permission`）・アセット非干渉方針（P2-5-7）を変更しない。

1. **ページ本文に載る操作（地図 GUI 編集・draw.io 保存・それらの閲覧）** は、本文を介するため既存の **page view/edit 権限がそのまま適用**される（別権限を新設しない）。保存は `save_page_body` 単一経路を通り、リビジョンに記録される。
2. **コメント** は専用の操作だが権限はページに準じる: 一覧・投稿は **view 権限**、編集・削除は **投稿者本人 or edit 権限 or 管理者**（要件 3A-C-9〜11）。コメントはページ権限の判定ヘルパ（`require_page_permission`）を流用し、独自の階層判定を作らない。
3. **アセット操作（CAD 変換アップロード・写真アップロード・SVG 登録）** は、フェーズ 2 で確定したとおり **ページ権限の対象外**（アセットは独立共有リソースで 1 アセットが複数ページから参照されうる、P2-5-7・U-5）。本フェーズでアセット単位の閲覧/配信権限を新設しない。この結果、`JANUS_REQUIRE_AUTH` に基づく認証を満たす利用者はアセットを登録・取得できる（`/api/assets/<id>/file` 直リンクを含む）点を、**セキュリティ上の明示事項**として据え置く（将来の専用課題、U-3A-2）。
4. **管理者（Django superuser）** は、フェーズ 2 の設計どおり `effective_permission` の管理者バイパスにより、権限エントリやデフォルトポリシーに関わらずページ系操作（コメントのモデレーション含む）を行える。これは仕様（ユーザー確認済み: superuser は閲覧拒否を受けないのが仕様）であり本フェーズでも維持する。
5. **フロント表示制御は補助**。編集 UI（地図 GUI・draw.io・コメント編集ボタン・CAD/写真アップロード）の出し分けは `getEffectivePermission` 等の利便性のためで、**セキュリティ境界はサーバー**が担保する（P2-5-5）。

## StorageClient 契約への追加（foundation 要件 1・P2-13）

本フェーズの新機能はすべて `StorageClient` 契約（`frontend/src/storage/types.ts`）に表現し、既存メソッドシグネチャを破壊せず**追加のみ**で拡張する。ローカルモード（3b）が同契約を満たせる抽象度を保つ。

1. **コメント**: 新 `CommentClient` 契約（例: `listComments(path)`／`addComment(path, body)`／`updateComment(id, body)`／`deleteComment(id)`）を定義し `StorageClient` に合成する。指定子は数値 ID を基本とする（phase2 の `PermissionClient` と同流儀）。
2. **CAD 変換**: **`StorageClient`/`AssetClient` 契約には追加しない**。CAD→SVG 変換はブラウザ内で完結するクライアント内ユーティリティ（記法シリアライザと同じく契約外のフロント実装）であり、変換後 SVG の登録のみ既存 `AssetClient.uploadAsset` を使う。したがって契約面は「写真アップロードと同じ `uploadAsset` を使う」だけで足り、CAD 固有の契約メソッドを増やさない。これによりサーバー非関与という事実を契約に漏らさず、3b はこの変換ユーティリティと `uploadAsset`（ローカル実装）をそのまま再利用できる。
3. **draw.io・地図 GUI 編集**: いずれもページ本文に載るため、保存は既存 `updatePage`/`createPage`（内部で `save_page_body`）経由で足り、**新しい保存系契約を増やさない**（本文テキストの編集として扱う）。描画 XML・地図記法の生成/パースはフロント内のユーティリティ（記法シリアライザ）として実装し、契約には載せない。
4. **写真アップロード**: 既存 `AssetClient.uploadAsset` をそのまま用いる（新規契約なし）。
5. THE 新規契約 SHALL foundation 要件 1-3 の「同一契約を IndexedDB 実装で満たせる抽象度」を保つ。CAD 変換はクライアント内ユーティリティ + 既存 `uploadAsset` の組み合わせで表現し、契約に新規メソッドを足さないため、サーバー/ローカルの差を契約に漏らさない。

## 非機能要件

1. **後方互換（最優先）**: フェーズ 1/2 の API 契約・レスポンス必須フィールド・既定挙動を破壊しない。新規モデル（コメント等）は追加マイグレーション（0005 以降）で導入し、既存 `Page`/`Folder`/`Asset`/`PagePermission`/`Revision` の破壊的スキーマ変更を行わない。既存の約 145（backend）/ 約 132（frontend）テストを回帰させない。
2. **セキュリティ境界**: すべての可否判定の最終決定はサーバー側（`require_page_permission`・ビュー内判定）で行う。生 HTML 無効方針（rehype-raw 不採用）を維持し、コメント本文・draw.io XML・地図記法いずれも XSS 経路を作らない形で保持/描画する。
3. **軽量性・移植性**: foundation 要件 12/13 を損なわない。CAD 変換は**ブラウザ内**で行い、サーバーに変換依存（ezdxf 等）を一切追加しない（最小構成 = Python 1 プロセス + SQLite を阻害しない）。フロント側は変換に必要なライブラリ（`ezjww`/`dxf-parser`/`iconv-lite`）を追加するが、WASM の Vite 読み込みや bundle サイズ影響を設計で評価し、閲覧専用の軽量さを損なわない。追加のフロント UI フレームワークは入れない（素の CSS Modules 流儀を維持）。draw.io 同梱配布物の bundle サイズ影響も設計で評価する。
4. **DB 移植性**: 新規スキーマ・クエリは **SQLite で成立**することを必須とし、PostgreSQL 移行を阻害しない（SQLite 固有機能に依存しない。ユーザー方針により PostgreSQL 対応は後回し）。
5. **契約の一本化**: 新機能は `StorageClient` 契約に閉じ込め、ローカルモード（3b）が同契約を満たせる抽象度を保つ（foundation 要件 1）。
6. **記法・パーサ非破壊**: 地図 GUI 編集は既存パーサが読める記法のみを生成し、既存の `:::custom-map` 表示・テストを壊さない（往復無損失・エスケープ整合）。

## 受け入れ基準（統合・テスト観点のサマリ）

本フェーズ完了時、以下がテストで検証可能であること（SQLite で全成立）。番号は検証項目。

1. ページに view 権限のある利用者がコメントを投稿でき、本文・日時・投稿者が記録される。
2. コメント一覧が view 権限で取得でき、権限なしは 403（秘匿時 404）。
3. 投稿者本人・edit 権限者・管理者はコメントを編集/削除でき、無関係な一般利用者は 403。
4. ページ削除でそのページのコメントが連動削除され、投稿者ユーザー削除でコメントが残り投稿者が null 化する。
5. コメント操作が `Page.body`・リビジョンに影響しない。
6. CAD（.jww/.dxf）を選ぶとブラウザ内で SVG へ変換され、既存 `uploadAsset` でアセットライブラリに 1 件登録され、向き 0/90/180/270 の焼き込み指定が SVG に反映される（サーバーは変換に関与しない）。
7. CAD 変換の失敗（未対応・破損・エンティティ上限超過・WASM 読み込み不可等）がフロントエンドの明確なエラー表示で通知され、通常画像/SVG アップロードへ案内され、アセットが登録されず孤児も残らない。重い図面でも上限・ローディング表示・（可能なら）Worker により UI がハングしない。
8. 登録 SVG が地図記法から `filename:`/`alias:` で解決・表示でき、`<img>`（Blob URL）で安全に描画される。元 CAD は保持されない。
9. draw.io（セルフホスト同梱）で作図した XML がページ本文に保持され、`save_page_body` 経由でリビジョンに記録される。実行時に外部ドメインへ接続しない。
10. 描画を含むページの閲覧で図が同梱ビューアでレンダリング表示され、既存 Markdown・`:::custom-map` と共存して壊れない（生 HTML 無効を維持、外部ドメイン非依存）。
11. 地図 GUI 編集でマーカー配置・ラベル/色/説明/座標を設定し、生成記法が既存パーサで同一 `MapData` に読み戻せる（往復無損失）。
12. GUI 生成記法が既存コンテナ属性・マーカー・写真の記法仕様のみを用い、特殊文字が往復で保たれる。
13. 地図 GUI 編集・写真紐付けの保存が `save_page_body` 経由でページ本文・リビジョンに反映される。
14. 既存画像/写真を選択アップロードしてマーカーの参考写真として紐付けでき、`CustomMapViewer` の写真ポップアップで表示される。
15. アセット操作（CAD 変換後 SVG の登録・写真アップロード）が既存 `uploadAsset` 経由でフェーズ 2 のアセット権限ポリシー（ページ権限非干渉・認証のみ）に従う。
16. 新機能が `StorageClient` 契約の追加のみ（コメントのみ）で表現され、既存シグネチャが不変。CAD 変換は契約に新規メソッドを足さない（クライアント内ユーティリティ + 既存 `uploadAsset`）。
17. 既存フェーズ 1/2 のバックエンド/フロントテストが全合格し続ける（回帰ゼロ）。
18. 新規マイグレーションが SQLite で成立し、既存データを保全する。

## スコープ外（本フェーズ 3a で扱わない）

- **ローカルモード（foundation 要件 10）** = PWA + IndexedDB + オフライン動作 + **端末カメラ API による撮影** → **フェーズ 3b**。3a は同一 `StorageClient` 契約を 3b が満たせる抽象度の担保のみ。
- **現場写真の撮影（カメラ起動）**（foundation 要件 3-5 の撮影部分・10-4）→ 3b。3a は既存ファイルの選択アップロードまで。
- **ローカルモードの実装そのもの**（IndexedDB 版 `uploadAsset`・PWA・オフライン基盤）→ 3b。ただし 3a で作る CAD ブラウザ変換ユーティリティと draw.io セルフホスト同梱は、3b がそのまま再利用できる形で実装する（foundation 要件 8-3 の「事前変換取り込み」はブラウザ変換により「端末内直接変換」へ改善。要件 3A-CAD-1/8 参照）。CAD の端末内変換・draw.io のオフライン編集を 3b で**追加実装なしに**成立させることが 3a の設計目標であり、「できないことにする」制約は置かない。
- **フェーズ 2 の後続改善**（phase2 tasks.md 末尾で合意済み）: 権限付与 UI でのユーザー名/グループ名指定、新規ページ作成フロー内での初期権限設定 → 本フェーズでは扱わない（関連箇所に触れる場合は参照のみ）。
- **アセット単位の閲覧/配信権限**（P2-5-7・U-5）→ 将来の専用課題。本フェーズでアセット権限を新設しない（CAD 変換・写真も認証のみ）。
- **全文検索**（foundation 要件 11）→ フェーズ 4。
- **ローカル ⇔ サーバー同期（B 案）**（foundation 将来拡張）→ スコープ外。本フェーズのデータ形式（コメント・描画 XML・地図記法）は同期を阻害しない自己完結形式に保つのみ。

## foundation / phase2 との関係（重複・矛盾の扱い・所有の明確化）

- **要件の具体化**: 本書は foundation 要件 7/8/9/3-4/3-5 を 3a として実装レベルに具体化する。foundation・phase2 の要件書は変更しない。
- **コメントの連動/null 挙動**: foundation 要件 7-4（ページ削除でコメント連動削除）を本書 3A-C-5 で踏襲し、投稿者削除時の null 化（3A-C-6）を phase2 の `Revision.author` SET_NULL と同方針で新規に定義する。
- **CAD 変換とアセットライブラリ**: foundation 要件 8・14-6 の「変換は登録手段の一つ」「元 CAD は保持しない」を本書 3A-CAD で確定。本フェーズでは**変換をブラウザ内で行い**、登録のみ既存 `AssetClient.uploadAsset` を使う（サーバーは変換に非関与）。アセット登録の一意制約・重複 409・物理フラット保存は既存 `Asset`（foundation design 3 章）をそのまま使う（本書で新スキーマを足すのはコメントのみ。CAD/描画/地図/写真は既存 `Asset`/`Page` に載せる）。foundation 要件 8-3 の「ローカル = 事前変換済み取り込み」はブラウザ変換により「端末内直接変換」へ改善される。
- **描画 XML の保持場所**: foundation design 11 章「本文中コードフェンス or 専用ディレクティブ」の未決を本書 3A-DRAW-3 で「設計時に 1 案へ確定」と課した（本書では案を 1 つに固定せず、設計書で選定・ロックする）。保存は phase2 `save_page_body` 経由（リビジョン整合）。
- **地図記法の所有**: `:::custom-map` 記法仕様は foundation（表示）/本フェーズ（GUI 生成）が共有する。**記法仕様の正は foundation の `parse-map.ts`**。GUI はそれに従属し記法を変えない（本書 3A-MAP が従属関係を明記）。
- **権限の所有**: ページ view/edit 権限の判定は phase2（`permissions_logic`/`require_page_permission`）が所有。本フェーズはそれを流用するだけで新しい判定規則を作らない。アセット非干渉（P2-5-7）も phase2 の判断を据え置く。
- **保存単一経路の所有**: 本文を変える操作（地図 GUI・draw.io）は phase2 の `save_page_body` が所有する単一経路を通す。本フェーズで別の本文保存経路を作らない。
- **完了状態の非上書き**: フェーズ 1/2 の完了判定（既存受入基準・既存テスト）を覆さない。既存挙動を変える必要が生じた場合は設計書で「foundation/phase2 変更か 3a 追加か」を明記し、既存の完了判定を破壊しない範囲に限定する。

## ユーザー判断が必要な未確定事項（設計レビューで確認）

合理的な推奨案を置いて実装を進めるが、以下は運用・セキュリティ・実現可能性に影響するため設計レビューで最終確認する。

- **U-3A-1（コメント投稿に必要な権限）**: 投稿は **view 権限で可**（閲覧できる人はコメントできる）を推奨。編集・削除は投稿者本人 or edit 権限 or 管理者。「投稿は edit 権限を要する」運用にしたい場合は要確認。
- **U-3A-2（アセット権限の据え置き）**: CAD 変換・写真アップロードを含むアセット操作をフェーズ 2 どおりページ権限の対象外（認証のみ）とする（推奨）。`/api/assets/<id>/file` 直リンクで認証ユーザーがアセットを取得しうる点は据え置き。アセット権限を本フェーズで前倒しする必要があれば要確認。**セキュリティ境界に関わるため要確認。**
- **U-3A-3（CAD 変換の対応フォーマットと変換方式）— 確定済み**: ユーザー確認により、**変換はブラウザ内で行い（サーバー非関与）**、対象は **.jww（主）/.dxf の両方**とする。JWW は `ezjww`（WASM）、DXF は `dxf-parser`+`iconv-lite` を用い、参考実装（`jww-to-svg.js`/`dxf-to-svg.js`）から移植する（基準 3A-CAD-1/6/7）。実機での変換成立（WASM の Vite 読み込み含む）は実装初手のスパイクで確認する。
- **U-3A-4（draw.io XML の保持形式）**: コードフェンス方式か専用ディレクティブ方式か（3A-DRAW-3）。既存 `:::custom-map`（ディレクティブ）との一貫性からディレクティブ方式が親和的だが、生 HTML 無効・複数図・同期非阻害の観点で設計時に 1 案へ確定する。
- **U-3A-5（draw.io エディタ提供方式とオフライン）— 確定済み**: ユーザー確認により、**セルフホスト同梱**（diagrams.net コア Apache-2.0 を同梱・自前配信、公開 `embed.diagrams.net` は不採用）とする（3A-DRAW-1/6）。実行時に外部ドメインへ依存せず、オフライン編集も成立する前提。同梱配布物の構成・Vite 配信・bundle サイズ影響は設計で確定し、実装初手のスパイクで検証する。
- **U-3A-6（コメントのレンダリング）**: コメント本文をプレーンテキスト扱いにするか限定的 Markdown にするか（3A-C-7）。XSS 回避のため既定プレーンテキストを推奨。
- **U-3A-7（CAD 変換失敗の表現）— 確定済み（ブラウザ変換により HTTP ステータス不要）**: 変換はブラウザ内で行いサーバーに変換エンドポイントを持たないため、失敗は HTTP ステータスではなく**フロントエンドのエラー表示**で表現する（3A-CAD-5）。失敗時は明確なメッセージと「通常画像/SVG アップロードへの案内」を提示する。
